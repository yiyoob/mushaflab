## D69: Storage: line-per-fact text in git, compiled to SQLite
Status: accepted (Yusuf and Eisa, 2026-11-23; relayed by Eisa)
Date: 2026-11-23
Context: The legacy data was ~120 MB of generated YAML, parsed at about 5 MB/s by the Rust loader
(15 s per load, measured 2026-11-21). The new data is curated from books, reviewed by the owner,
and must keep provenance per fact.
Options:
| Option | Load ~50 MB | Review a change | Concurrent editors |
| --- | --- | --- | --- |
| YAML | ~10 s at the measured rate | readable, noisy diffs | git merges |
| TSV / JSONL, one fact per line | under 1 s | one changed line per fact, with blame | git merges |
| SQLite committed to git | instant | binary: no diff, review or merge | none |
| Database server | instant | needs an export | yes |
Decision: The source of truth is text in `corpus/`: TSV for large tables, JSONL where a row
nests, YAML only for small hand-written files (profiles, writing conventions). `mushaf build`
compiles it into `build/corpus.db` (SQLite), which the engine, the web bundle, the review page and
queries read; it is never edited. Revisit when several people who don't use git edit at once:
then a database (or Dolt) becomes the editing surface and exports to the same files.
Consequences: Provenance per fact through `git blame`; the owner reviews a PR as changed rows;
builds are deterministic (rule 8). Column definitions live in `docs/formats.md`.
